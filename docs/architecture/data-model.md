# Data model and analytics

This document describes what the PostgreSQL database holds, grouped by domain, and how the analytics
pipeline works: where the event list comes from, how events are stored and summarised, which
scheduled jobs maintain them, and what the numbers can and cannot be used to claim. Read it before
changing a schema file, writing a migration, adding an analytics event or presenting figures to a
business owner.

## Where the schema lives

The Drizzle schema is in `packages/db/src/schema/`, one file per domain, re-exported from
`index.ts`. Enums (roles, statuses, link types, draft language) are in `enums.ts`. Migrations are SQL
files in `packages/db/drizzle/`, generated by drizzle-kit (`pnpm db:generate`) and applied by
`pnpm db:migrate`, which prefers `DIRECT_DATABASE_URL`. There are ten migrations today, `0000` to
`0009` (see `packages/db/drizzle/meta/_journal.json`). **Never edit a migration that has been
applied**; add a new one.

The database needs PostgreSQL 17 or newer: `analytics_events` declares an identity column on a
partitioned table, which older versions reject. Migration `0000` also enables the `citext` and
`pgcrypto` extensions. Emails and slugs are `citext` (case-insensitive).

Rules the schema enforces that code relies on:

- **One primary review destination per business.** `review_destinations` is the single source of the
  Google review URL. The `GOOGLE_REVIEW` row in `business_links` only controls whether and where the
  button renders and must carry no URL of its own (check constraint).
- **Exactly one active review mode** per business (`uq_one_active_mode`) and **exactly one ACTIVE
  prompt version** platform-wide (`uq_one_active_prompt_version`).
- **Slugs share one namespace.** A renamed business keeps its old slug as a non-primary row with
  `redirect_until` (180 days), so printed links keep working.
- **Counters on `subscriptions`.** Free and Pro draft usage are separate counters with their limits on
  the same row, so a reservation is one conditional `UPDATE`. The limits are copied from
  `platform_settings` when the business signs up. A trigger from migration `0003` resets the Pro
  counter when a new paid period starts. See [billing and plans](../features/billing-and-plans.md).
- **Payments keep snapshots.** An invoice stores the amount, tax breakdown, and seller and buyer
  details as they were, so later price or settings changes never rewrite history.
- **Tenant data cascades.** Most business-owned tables reference `businesses.id` with
  `ON DELETE CASCADE`. `businesses.deleted_at` (soft delete) is honoured by every public resolver.

`platform_settings` is the source of truth for the Free and Pro allowances, the Pro price and the
seller/GST details; admins edit it at `/admin/settings`. A key with no stored row falls back to
`PLATFORM_SETTING_DEFAULTS` in `packages/core/src/platform/settings.ts`. The
`FREE_AI_GENERATION_LIMIT`, `PRO_ANNUAL_GENERATION_LIMIT` and `PRO_ANNUAL_PRICE_PAISE` environment
variables are still accepted by the configuration schema, but nothing reads them.

## Analytics events

### Where the event list comes from

The allowed events and their properties are defined by `docs/spec/11_Analytics_Event_Taxonomy.csv`
(event name, actor, trigger, required properties, optional properties). It belongs to the frozen spec
pack, so a new or changed event is a spec change to be recorded in
[spec amendments](../decisions/spec-amendments.md) before code writes it.

`packages/analytics/scripts/generate-events.ts` turns the CSV into
`packages/analytics/src/events.generated.ts` (`pnpm --filter @ai-review/analytics generate`). CI
regenerates it and fails if the committed file differs. From the generated list:

- `EventPayload<'event_name'>` makes a server-side insert with a missing or unknown property a
  compile error.
- `POST /api/v1/public/events` accepts any event name in the taxonomy (`isEventName`), not only the
  ones the browser normally sends. It injects `business_id`, `anonymous_session_id` and `qr_code_id`
  from server-resolved state rather than trusting the request, then checks the payload at runtime
  with `validateEvent`; an unknown name or an invalid payload is dropped with a 202.
- `FUNNEL_EVENTS` is the customer funnel: `qr_scan` → `review_page_view` → `ai_generate_success` →
  `review_copy` → `google_open`. It deliberately ends at `google_open`.

The 23 events cover the public flow (scan, page view, generate click/success/failure, regenerate,
edit, experience confirmed, copy, Google open, private feedback open/submit, profile view and link
click), review requests (prepared, marked sent, link click) and owner/admin actions (QR created,
custom domain, checkout started, subscription activated, business suspended).

### How events are stored

`analytics_events` is `PARTITION BY RANGE (occurred_at)`, monthly, with a default partition
(`analytics_events_default`) for rows outside any month partition. The partitioned DDL and the
`ensure_analytics_events_partition()` function are hand-written in migration `0000` because Drizzle
cannot express partitioning, so the Drizzle snapshot describes an ordinary table. **Do not accept a
generated migration that alters this table blindly.** `scripts/db/check-migrations.mjs`
(`pnpm check:migrations`, run in CI) fails on destructive changes to it.

Events carry identifiers and non-personal properties only. A customer's name, mobile or feedback
text never goes into an event.

### How figures are read

`apps/web/lib/analytics/queries.ts` combines two sources:

- **Range totals, the funnel and distinct-session counts** are counted live from `analytics_events`
  (distinct counts cannot be summed across days).
- **Daily trends** use `analytics_daily_business` for completed business-local days, today's figures
  come live, and a completed day the rollup has not reached yet is shown as **pending**, never as
  zero. Day boundaries use each business's own `timezone`.
- **Per-QR and per-link breakdowns** are always live queries.

## Scheduled maintenance

`GET /api/cron/maintenance` (daily; see the
[schedule](../operations/email-and-scheduled-jobs.md#vercel-cron-jobs)) runs the loop in
`apps/web/lib/cron/maintenance.ts` within a 30-second budget. Its database store,
`apps/web/lib/cron/maintenance-store.ts`, uses SQL shared with the worker through
`@ai-review/worker/maintenance`:

1. **Housekeeping** — creates the analytics partitions for the next few months
   (`WORKER_PARTITION_MONTHS_AHEAD`, default 3), reports how many rows sit in the default partition,
   and deletes expired login `sessions` in batches after a grace period
   (`WORKER_SESSION_PURGE_GRACE_DAYS`, default 7).
2. **Analytics rollups** — fills `analytics_daily_business` business by business, day by day,
   checkpointing progress in `maintenance_jobs` after each unit.

Each part holds a transaction-level advisory lock, so overlapping runs answer `busy`. The response
status is `complete`, `pending` (the next run resumes from the checkpoint) or `busy`. The Cron path
never drops old partitions; the worker's partition dropping is off unless
`WORKER_PARTITION_DROP_ENABLED` is set. `anonymous_sessions` rows are not purged by any job today.

`GET /api/cron/subscriptions` also deletes `user_activity_logs` rows older than
`ACTIVITY_RETENTION_DAYS` (default 180).

## What analytics can and cannot claim

- Figures are **event counts and distinct anonymous sessions**. A session is a browser cookie scoped
  to one business, not a person.
- The last observable step is `google_open`: the customer's browser opened the review page.
  **Nothing records whether a review was posted**, what it said or what rating it had. Never label a
  figure "reviews", "reviews submitted" or "ratings"; ESLint (`pnpm lint`, run in CI) fails on text
  such as "review submitted" (rule AC-025 in `eslint.config.mjs`).
- Browser-sent events (`review_copy`, `google_open`, `review_edit`, `experience_confirmed`, clicks)
  are best-effort telemetry. They can be blocked or lost, and `review_copy` is sent only when the
  clipboard write succeeded.
- `review_page_view` is recorded only by the QR route (`/r/{code}`); `/{slug}/review` does not emit
  it, so visits through links are under-counted at that step.
- The product collects no star ratings and no sentiment, so there is none to report.
