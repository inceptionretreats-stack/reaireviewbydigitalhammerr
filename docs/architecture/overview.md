# Architecture overview

This document explains how Ai Review is put together: the deployable parts, the internal packages
they share, where each kind of code goes, what runs where in production, and the full map of the
repository. Read it first if you are new to the codebase; the other architecture documents
([routes](routes.md), [data model](data-model.md), [security](security.md)) and the
[feature documents](../features/) go deeper into individual areas.

## The system at a glance

There is one deployable application. The backend is not a separate service: it is the set of
Next.js App Router route handlers under `/api/v1` inside `apps/web`, backed by shared domain code in
`packages/`.

```text
Visitor / vendor / customer / admin browser
                |
                v
apps/web  (Next.js 16 on Vercel)
  proxy.ts ............ runs first: migration gate, auth-host redirect, anonymous cookie
  app/ pages .......... React Server Components per audience
  app/api/v1/* ........ JSON API (route handlers)
  lib/* ............... logic shared by routes and components, by concern
                |
                +--> packages/core ...... domain logic: Ai, prompts, quota, billing, auth, tenancy
                +--> packages/db ........ Drizzle schema + pg pool --> PostgreSQL (hosted on Supabase)
                +--> Redis .............. shared rate-limit counters (in-memory fallback per process)
                +--> Ai provider ........ Anthropic, OpenAI or Gemini, chosen by which key is set
                +--> Razorpay ........... Pro checkout orders, payment verification, webhooks, refunds
                +--> Resend ............. transactional email (reset links, invites, receipts, reminders)

Vercel Cron --> app/api/cron/* --> subscription sweep, health check, analytics/partition maintenance
apps/worker (optional, not deployed) --> the same maintenance jobs scheduled on BullMQ + Redis
```

## How the parts depend on each other

`apps/web` uses all six internal packages plus the worker's maintenance helpers; `apps/worker` uses
`analytics`, `config`, `core` and `db`; among the packages only `core` depends on another (`db`).
The full table is in [packages](../../packages/README.md#dependency-direction). Points worth knowing:

- **Packages are source-only.** Each package under `packages/` points `main` at `src/index.ts`, and
  the worker exports TypeScript source too. Nothing is pre-built;
  `apps/web/next.config.ts` lists every workspace package in `transpilePackages`, so Next compiles
  them with the app and the web app and worker share one implementation.
- **The web → worker import.** `apps/worker/package.json` exports exactly one subpath,
  `@ai-review/worker/maintenance` (`apps/worker/src/maintenance.ts`). It re-exports side-effect-free
  helpers: the analytics daily-rollup store, the partition store and the business-local date
  functions. `apps/web/lib/cron/maintenance-store.ts` uses them so the Vercel Cron path runs the same
  SQL as the worker. The worker's startup entry (`apps/worker/src/index.ts`, which connects to Redis
  and starts BullMQ) is never imported by the web app.
- **Server-only code stays server-only.** `apps/web/lib/infra/env.ts` validates the environment
  through `@ai-review/config` and must never be imported by a client component. Client components
  also avoid value imports from `@ai-review/core`'s root, which pulls in `pg` and Argon2.
- **One error envelope.** API errors are `{ "error": { "code", "message" } }` with the HTTP status
  fixed per code in `apps/web/lib/http/api-error.ts`.

### Where new code goes in `apps/web`

- **Pages and route handlers do the work for their own URL.** A handler calls a guard
  (`requireTenant`, `requireAdmin` or a public resolver), parses the request, does its work and
  shapes the response; a page loads what its own screen shows. Either may query the database
  directly with Drizzle when the query serves only that page or endpoint. About 16 pages and 22
  handlers do this today (`git grep -l "from 'drizzle-orm'" -- apps/web/app` lists them).
- **Logic used by more than one place goes in `apps/web/lib/<concern>/`**: guards, sessions, a
  query used by two routes or by a page and a route, request parsing, view models. This is the rule
  for new code: when a second place needs something that lives in a route file, move it to `lib/`.
  A few older helpers still break it; they are listed
  [below](#helpers-still-copied-between-files).
- **A helper used by only one route may sit beside that route**, because a Next route module may
  export only its HTTP methods and route config. Example:
  `apps/web/app/api/v1/ai/test-preview/preview-limit.ts`.
- **Domain rules the worker also needs go in `packages/core`.**
- **Import direction is enforced for two folders.** ESLint fails the lint step when a file in
  `apps/web/lib/` imports `components/` or `app/`, or a file in `apps/web/components/` imports
  `app/` (tests are exempt). See [`lib/`](../../apps/web/lib/README.md#import-rules).

#### Helpers still copied between files

These small helpers are still defined privately, with the same body, in more than one file (paths
under `apps/web/`). Move each one to `lib/` when you next touch one of its copies, and make every
copy import it:

- `refuseFrozenTenant` — `app/api/v1/business/route.ts`,
  `app/api/v1/business/review-destination/route.ts` and `app/api/v1/business/links/[id]/route.ts`.
  `lib/ai/modes/guards.ts` exports a function of the same name that gives the same answer but takes
  the business status instead of the tenant context.
- `passwordMessage` — `app/api/v1/auth/signup/route.ts`, `app/api/v1/auth/reset-password/route.ts`
  and `app/api/v1/account/password/route.ts`.
- `isUniqueViolation` — `app/api/v1/business/publish/route.ts`, `app/api/v1/qr/route.ts`,
  `app/api/v1/business/links/[id]/route.ts` and `lib/ai/modes/mode-service.ts`.
  `lib/infra/safe-error.ts` already exports one, which also looks through the error's `cause` chain.
- `isHttpsUrl` — `app/api/v1/business/links/route.ts`, `app/api/v1/business/links/[id]/route.ts`
  and `components/dashboard/profile/ProfileEditor.tsx`. `components/onboarding/link-fields.ts`
  exports another copy for the onboarding form. Both component copies run in the browser, so the
  shared version must live in a client-safe `lib/` module.
- `assetUrl` — `app/(customer)/[slug]/page.tsx` and `app/(vendor)/app/profile/page.tsx`, with a
  third variant, `buildAssetUrl`, in `lib/customer/public-business.ts`. All three build a logo URL
  from `S3_PUBLIC_BASE_URL`.

## Hosting

This is the production shape at a high level. The current operational guides are the
[deployment checklist](../operations/deployment-checklist.md) and
[database on Supabase](../operations/database-supabase.md). The
[first Vercel deployment runbook](../history/2026-09-17-vercel-deploy-runbook.md) is a historical
record; parts of it no longer apply.

- **App and API — Vercel.** One Vercel project with Root Directory `apps/web`.
  `apps/web/vercel.json` pins the function region (`sin1`) and declares three Cron jobs (see
  [routes](routes.md#scheduled-jobs-vercel-cron)). Routes that wait on an Ai provider set
  `maxDuration = 60`.
- **PostgreSQL — hosted on Supabase, used as plain PostgreSQL.** The app connects with
  `DATABASE_URL` through `pg` (pool per process, `apps/web/lib/infra/db.ts`); migrations prefer
  `DIRECT_DATABASE_URL`. There is no Supabase Auth and no Supabase client library, and nothing in the
  browser talks to the database: the Data API is disabled and every table has RLS enabled with no
  grants to the API roles.
- **Authentication — the application's own.** Accounts live in `public.users` and sessions in the
  `sessions` table, not in Supabase `auth.users`. See [security](security.md).
- **Redis.** `REDIS_URL`. Holds rate-limit counters. When Redis is unreachable the limiter falls back
  to per-process memory. BullMQ uses Redis only in the optional worker.
- **Ai provider.** Whichever of `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` is set, in
  that order of precedence. Production configuration fails validation with none. Which provider
  production last used is recorded in [Ai generation](../features/ai-generation.md#providers).
- **Payments — Razorpay.** Orders API on the server, Checkout.js in the browser, and a signed webhook.
  See [billing and plans](../features/billing-and-plans.md).
- **Email — Resend.** REST API when `RESEND_API_KEY` is set; console output in development without
  it.
- **Background work.** Vercel Cron calls `/api/cron/*`. `apps/worker` is a standalone BullMQ process
  that is implemented but not deployed; do not run both schedulers against one database without
  deciding which one owns the jobs.

Configuration fields that exist but are not wired to a working integration: the `S3_*` upload fields
(only `S3_PUBLIC_BASE_URL` is read, to build URLs for already-stored logos), `SES_REGION`,
`CLOUDFLARE_*` (custom domains use an unconfigured provider in the worker), `SENTRY_DSN` and
`OTEL_EXPORTER_OTLP_ENDPOINT`. Their presence in `.env` does not mean the feature works. Every
variable is listed by name in [environment variables](../operations/environment.md).
